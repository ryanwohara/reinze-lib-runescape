# Params tables: migrate Database.ini into per-skill Rust

Date: 2026-08-02

## Problem

`+params <skill> <query>` answers "how much XP is this" from `lib/Database.ini`,
a 116 KB file of 23 sections and 5,920 entries. The file lives in the **bot**
repo, `rust-reinze`, while its only consumer — `src/params.rs` — lives in this
repo, the plugin. Nothing else reads it.

That split has costs:

- `Ini::load_from_file("lib/Database.ini")` resolves against the **bot's**
  working directory at runtime, so the data cannot move without breaking the
  load.
- The file is re-read and re-parsed on **every** invocation of the command.
- Validating a data change means creating a throwaway binary in this repo to
  check a file in the other one. The three audits that re-derived these
  sections each had to do exactly that, once per task.

The seven hand-maintained sections were audited and merged on 2026-08-01 and
2026-08-02, so the data is now trustworthy. This migration changes how it is
stored, not what it says.

## Goal

One Rust file per skill, generated from the INI, which moves into this repo and
remains the thing a human edits.

## Scope

**In:** the 17 non-combat skills — Agility, Construction, Cooking, Crafting,
Farming, Firemaking, Fishing, Fletching, Herblore, Hunter, Magic, Mining,
Prayer, Runecraft, Smithing, Thieving, Woodcutting. 2,508 entries, 29
(Agility) to 495 (Crafting) per skill.

**Out:** Attack, Strength, Defence, Ranged, Hitpoints and Slayer — 3,412
entries. They keep coming from the INI. See below for why they are not folded
into `npc/data.rs` here.

### Why combat and Slayer are deferred

`NpcMetadata` already carries `combat_xp`, `hitpoints_xp` and `hitpoints`, and
the INI's combat sections are a second copy of that data: Attack, Strength,
Defence and Ranged hold an identical value for all 637 monsters, Hitpoints
holds `hitpoints_xp`, and Slayer's values match each monster's HP level.
Consolidating looks obvious and is not:

- `npc/data.rs` describes **2,872** monsters against the INI's **637**.
- After normalising case and stripping punctuation, only **39%** of Attack
  keys and **29%** of Slayer keys match any npc name. `Abyssal_Demon`,
  `Angry_bear_(lvl_40)` and `Baby_black_dragon` have no counterpart.
- Slayer's 227 entries are a curated subset with no derivable filter —
  `slayer_req` is a requirement, not an assignability flag — and 6 of its keys
  are absent from Hitpoints entirely.
- Some npc names are malformed by their own generator, e.g.
  `ChickenGordon and Mary's Farm`.

Swapping the source would change what `+params attack dragon` even means:
637 candidates become 2,872, and roughly 60% of currently reachable keys are
renamed or lost. That is a product decision about the answer set, not a
mechanical migration, and it gets its own spec.

## Design

### Layout

```
src/params.rs             hand-written: command, module list, dispatch, drift test
src/params/agility.rs     generated
src/params/construction.rs
…17 files
```

`params.rs` and `params/` coexist under Rust 2018 module rules — the same shape
`npc.rs` and `npc/data.rs` already use in this crate.

The existing hand-migrated data files (`bolts.rs`, `patch.rs`, `plant.rs`) use
an enum per record with a `details()` method. That suits 20-60 structured rows
with several fields each. Params is a flat key-to-value map with up to 495 rows
per skill, so it needs a different shape; those files are not a convention to
inherit here.

### File shape

```rust
// @generated by bin/gen-params.py from lib/Database.ini — do not edit
pub const ENTRIES: &[(&str, &str)] = &[
    ("Adamant_2h_sword", "125"),
    ("Adamantite_bar", "37.5"),
];
```

Entries appear in **INI file order**, not re-sorted. This matters for one
section: `[Prayer]` is deliberately two blocks separated by a blank line —
bones and ashes, then ensouled heads — each sorted within itself, so the
section as a whole is not globally sorted. The generator preserves that order
and the drift test asserts it, so a well-meaning global sort would fail the
suite rather than silently reorder shipped output. Blank lines carry no data
and simply do not appear in the slice.

Values are `&str`, not numbers. Farming and Hunter carry composites —
`Apple_tree=22-1199.5-8.5` is plant/check/harvest XP, `Baby_impling=18/20` is
normal/Wilderness — and Woodcutting has `Bloodwood_(chop)=~30`. The lookup
never does arithmetic on these; it prints them.

`rank_matches` already takes `&[(&str, &str)]`, so both this and the INI path
feed it unchanged.

### Dispatch

Hand-written in `params.rs`: 17 `mod` declarations and

```rust
fn table_for(skill: &str) -> Option<&'static [(&str, &str)]> {
    match skill {
        "Agility" => Some(agility::ENTRIES),
        // …
        _ => None,
    }
}
```

`None` means "not a generated skill", and the caller falls through to the INI.
Adding a skill therefore means editing `params.rs`, not only regenerating — the
drift test below makes that omission loud rather than silent.

### The generator

`bin/gen-params.py`, matching the existing `bin/cmb-xp.py` → `src/npc/data.rs`
pattern: Python 3 standard library, run by hand, output committed. Not a
`build.rs` — this crate has none, and generation is rare enough that a build
dependency on Python would cost more than it saves.

### Combat and Slayer

`include_str!("../lib/Database.ini")` embeds the file at compile time; the six
remaining sections are parsed from that string with `Ini::load_from_str`. This
is what makes the move possible at all — a runtime load resolves against the
bot's working directory, so the file cannot leave `rust-reinze` and still be
found.

The parse result is cached in a `OnceLock`, so it happens once per process
rather than once per command. Today the file is re-read and re-parsed on every
invocation.

The embedded INI still contains the 17 generated sections, so the whole 116 KB
is compiled in while the runtime path reads only the six combat sections —
3,412 of 5,920 entries. The redundancy is the other 2,508. That is accepted over
having the generator emit a trimmed combat-only INI, which would add a build
artifact whose provenance is murkier than a single source file. When the
consolidation lands, the embed and those six sections go together.

### The drift guard

A Rust test in `params.rs` parses the embedded INI and asserts, in both
directions:

1. every generated slice is identical to its INI section — same keys, same
   values, same order;
2. every non-combat section in the INI has a module reachable through
   `table_for`.

Forgetting to regenerate, or adding a skill to the INI without wiring it up,
becomes a test failure naming the skill. This is what makes "the INI is the
source, the Rust is generated" safe rather than a standing trap.

## What moves and what is deleted

- `rust-reinze/lib/Database.ini` → `reinze-lib-runescape/lib/Database.ini`,
  deleted from the bot repo.
- The other files in `rust-reinze/lib/` are untouched. They belong to other
  commands and are outside this work.

## Out of scope

- Folding combat and Slayer into `npc/data.rs`. Deferred with reasons above.
- Any change to the XP values. The data ships exactly as audited; this is a
  storage change and the drift test proves it.
- The 10-result display cap, and the ranking added on 2026-08-02. Untouched.
- The other `lib/*.ini` and `lib/*.json` files in the bot repo.

## Verification

- `cargo test` passes, including the new drift test. The crate currently has
  188 tests.
- The drift test is the primary correctness gate: it proves the generated
  tables and the INI agree entry for entry.
- A before-and-after comparison of `+params` output for a sample of queries
  across several skills, confirming identical results. The ranking makes
  output order deterministic, so this is a straight comparison.
- `rust-reinze` builds and its tests pass with `lib/Database.ini` removed,
  confirming nothing there still reads it.
- No `.rs` file under `src/params/` is hand-edited; each carries the
  `@generated` header.

Two repositories.

In `reinze-lib-runescape`:

```
feat(params): generate per-skill tables from Database.ini
```

carrying the moved INI, `bin/gen-params.py`, the 17 generated files, the
rewritten `params.rs` and the drift test.

```

```
